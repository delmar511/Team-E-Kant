사전 예상은 "7/8 또는 8/8" 이었다. 맞았다.

## RRF 가 실제로 무엇을 했나

`src/diag_overlap.py` 로 두 검색기의 후보가 얼마나 겹치는지,
구성 B 의 상위 5개가 어디서 왔는지 확인했다.

```
문항            겹침/20        B상위5의 출처
DEV-001       1/20              *BVBV
DEV-002       4/20              ****V
DEV-003       7/20              *****
DEV-004       1/20              *BVBV
DEV-005      11/20              *****
DEV-006       9/20              *****
DEV-007       7/20              *****
DEV-008       0/20              BVBVB
평균 겹침 5.0 / 20
B=BM25에만, V=벡터에만, *=양쪽 모두
```

**겹침이 많은 문항은 상위 5개가 전부 `*` 다.** 두 검색기가 같이 찾아낸 문서가
`1/(k+rank)` 를 두 번 받아 한쪽에만 있는 문서를 밀어낸다. RRF 의 설계 의도 그대로다.

**겹침이 0인 DEV-008 은 `BVBVB` 로 교대한다.** 모든 문서가 점수를 한 번씩만 받아
동점이 무더기로 생기고, 정렬이 안정 정렬이라 먼저 넘긴 목록이 앞에 온다.
결과적으로 두 목록을 번갈아 배치한 꼴이 된다. 이 경우에도 정답은 5위 안에 들었다.

평균 겹침이 5/20 밖에 안 된다는 것도 기록해 둔다.
**두 검색기가 찾는 문서의 75%가 서로 다르다.** 둘을 합치는 이유가 여기 있다.

## 겪은 실수 — 들여쓰기 한 칸

처음 측정에서 구성 B 가 4/8 이 나왔다. BM25 단독과 문항별 O/X 가 완전히 같았다.

```python
    for lst in ranked_lists:
        for rank, (cid, _) in enumerate(lst, 1):
            scores[cid] = scores.get(cid, 0) + 1 / (k + rank)
        return sorted(...)          # <- 바깥 for 안에 있었다
```

`return` 이 바깥 `for` 블록 안에 있어서 **첫 번째 목록(BM25)만 처리하고 반환**했다.
벡터 목록은 돌지도 않았다.

처음엔 "겹침이 없어서 동점 때문에 BM25 가 앞선다" 고 추정했다.
그 추정이 틀렸고, 진단 스크립트를 돌려 코드를 다시 본 뒤에야 원인을 찾았다.
(다만 동점 때 교대 배치가 된다는 메커니즘 자체는 DEV-008 에서 실제로 관찰됐다.)

**파이썬은 들여쓰기가 곧 블록이라 이런 실수가 에러 없이 조용히 다른 동작을 한다.**
오류 메시지가 없고 결과도 그럴듯해서, 숫자를 의심하지 않았으면 그대로 넘어갔을 것이다.
BM25 단독과 문항별 결과가 글자 하나까지 같다는 게 단서였다.

## 남은 것

- `RRF_K = 60` 은 원 논문 권고값이다. 그 논문은 후보를 1000개씩 놓고 쓴다.
  우리는 20개라 1등(1/61)과 20등(1/80) 차이가 1.3배뿐이다.
  k 를 낮추면 상위 순위가 더 강조된다. 20문항 평가셋에서 k 를 바꿔 비교해 볼 만하다.
- 표본이 8문항이다. 8/8 은 천장에 닿은 값이라 더 올릴 여지를 알 수 없다.
  최종 평가셋(20문항)에서 다시 재야 한다.
- 구성 C(재정렬)를 8/8 위에서 측정하면 개선을 볼 수 없다.
  dev 로는 변별이 안 되므로 test 에서 비교해야 한다.
