# 임베딩 모델 비교 (구성 A)

- 일시: 2026-11-25
- 담당: 서종찬
- 평가셋: `eval/eval-dev.json` 8문항 (`no_answer` 2문항 제외)
- 재현: `python src/compare_embeddings.py text-embedding-3-small text-embedding-3-large`

## 측정 설계

**구성 A(벡터 단독)로 쟀다.** 구성 B 는 BM25 가 섞여 모델 차이를 가린다.
dev 에서 구성 B 는 이미 8/8 이라 어떤 모델을 넣어도 8/8 이 나왔을 것이다.

**Hit@5 외에 정답 청크의 순위를 같이 봤다.** Hit@5 는 1위로 찾은 것과
5위로 겨우 찾은 것을 똑같이 `O` 로 처리한다. 문항이 8개뿐이라 그 해상도로는
모델 간 차이를 판단할 수 없다. MRR(= 1/순위 의 평균)은 연속적인 값이라
같은 8문항에서 훨씬 많은 정보를 끌어낸다.

## 결과

```

text-embedding-3-small     1536     6/8   0.427     2  6  3  2  2  12  3  1
text-embedding-3-large     3072     7/8   0.701     1  2  2  1  1   9  2  1
                                                  001 002 003 004 005 006 007 008
```

| | 3-small | 3-large |
| --- | --- | --- |
| Hit@5 | 6/8 | **7/8** |
| MRR | 0.427 | **0.701** |
| 1위로 찾은 문항 | 1 | **4** |
| 전량 임베딩 비용 | ~$0.01 | ~$0.1 |
| 임베딩 소요 | 9.4초 | 13.8초 |

## 읽는 법

**8문항 전부에서 3-large 가 같거나 앞선다. 진 문항이 하나도 없다.**
이것이 Hit@5 차이(6 vs 7)보다 중요하다. 한 문항 차이는 우연일 수 있지만,
8문항 모두에서 밀리지 않는 것은 우연으로 보기 어렵다.

표본이 8개라 MRR 0.427 과 0.701 의 **절대값**은 믿을 게 못 된다.
믿을 수 있는 건 **방향이 일관되다는 사실**이다.

## [정정됨] 모델을 키워도 안 되는 것

> **아래 결론은 틀렸다.** OpenAI 모델 두 개만 보고 "벡터 방식 전체의 한계" 로 일반화했는데,
> 같은 날 KURE-v1 과 bge-m3 를 측정하니 둘 다 DEV-006 을 3위로 찾았다.
> 벡터 방식의 한계가 아니라 **OpenAI 모델의 한계**였다. 아래는 당시 기록 그대로 남긴다.

DEV-006 은 두 모델 모두 실패했다(12위, 9위).
`D-2-2`(학사)와 `D-2-3`(석사) **각각의** 허용 시간을 묻는 문항이다.

차원을 2배로 늘려도 9위가 한계였다. **벡터 방식 자체의 한계지 모델 품질 문제가 아니다.**
BM25 는 이 문항을 맞혔다(기준선에서 O). 보호 토큰이 코드를 통째로 지켰기 때문이다.

하이브리드가 필요한 이유가 여기서 한 번 더 확인된다.
좋은 임베딩 모델을 고르는 것으로는 이 구멍을 못 메운다.

## 결론

**`text-embedding-3-large` 를 쓴다.**

비용이 10배지만 절대액이 $0.1 대 $0.01 이다. 전량 재임베딩을 열 번 해도 1달러다.
이 규모에서 비용은 선택 기준이 되지 못한다.

## 1차 결론이 뒤집혔다

같은 계열 모델 둘을 보고 그 방식 전체로 일반화한 것이 원인이다.
`3-small`(1536) 과 `3-large`(3072) 는 차원만 다를 뿐 같은 집안이다.

**이 정정이 오늘 얻은 것 중 가장 값지다.** 측정하지 않았으면 틀린 채로 발표했을 것이다.

## 차원은 성능을 결정하지 않는다

1024차원 KURE-v1 이 3072차원 3-large 를 **모든 문항에서** 이긴다.
벡터가 3배 크다고 더 잘 찾는 게 아니다. 무엇으로 학습했는가가 결정한다.

## 한국어 추가 학습의 효과

KURE-v1 은 bge-m3 를 한국어로 추가 학습한 모델이다. **뼈대가 같고 학습만 다르다.**

| | MRR | 1위로 찾은 문항 |
| --- | --- | --- |
| BAAI/bge-m3 | 0.754 | 5 |
| nlpai-lab/KURE-v1 | **0.792** | **6** |

공개 벤치마크(MTEB-ko retrieval, nDCG@10)의 KURE-v1 0.762 > bge-m3 0.751 과
순서가 같다. 우리 데이터에서도 재현됐다.

## 공짜가 아니다

| | OpenAI 3-large | KURE-v1 |
| --- | --- | --- |
| 1,646청크 임베딩 | 13.8초 | 수 분 (CPU) |
| 설치 | 없음 (`openai` 패키지뿐) | PyTorch 포함 2~3GB |
| 모델 내려받기 | 없음 | 약 2.2GB |
| 비용 | ~$0.1 | 0 |
| 팀원 부담 | 키만 있으면 됨 | **전원이 설치해야 함** |

벤치마크 점수는 "더 잘 찾는다" 만 말한다.
"그 성능을 어떤 비용에 얻는가" 는 직접 재야 나온다.

## 측정하지 못한 것

- `text-embedding-ada-002` : 학원 프로젝트 계정에 접근 권한 없음 (403)
- `KURE-v2` : 토큰마다 벡터를 두는 late-interaction 방식이라
  현재의 단일 벡터 + 내적 구조로는 돌아가지 않는다. 저장과 검색을 모두 바꿔야 한다.
  MTEB-ko 에서 0.816 으로 KURE-v1(0.762)보다 높다. 구조 변경 비용과 맞바꿀지는 별도 판단.
