# eval-test.json 의 정답 chunk_id 는 버그의 산물이다

- 일시: 2026-11-26
- 담당: 서종찬
- 색인: `idx-v5` / 청크 1,815개 / 문서 39개 / `nlpai-lab/KURE-v1`

## 무엇이 잘못됐나

`eval-test.json` 의 근거에는 `quote` 가 없고 `page` 만 있다.
그 상태로 `src/link_evidence.py` 를 돌리면 다음이 일어났다.

```python
fragments('')     # -> ['']        빈 문자열 하나
'' in 아무문자열   # -> 항상 True
```

**모든 청크가 후보가 된다.** 그 뒤 같은 쪽으로 좁히고 **첫 번째 청크**를 골랐다.
질문 내용(`question`, `expected_facts`)은 한 번도 쓰이지 않았다.

그래서 이런 값이 박혔다.

| 문항 | 질문 | 지정된 정답 |
| --- | --- | --- |
| TEST-002 | D-2 유학생이 시간제취업 허가를 받기 위한 요건은? | `배우자(F-3) 체류자격외 활동 허가` |
| TEST-001 | D-4 어학연수생의 체류기간 연장허가 제출서류는? | `연수기관별 허용 쿼터 및 불체자 발생 제재` |

각각 37쪽·90쪽의 **첫 청크**였을 뿐이다.
`chunk_ids_all` 에 `DOC-A1`(외교)처럼 무관한 문서가 섞인 것도 같은 이유다 — 전부 후보였다.

**이 버그는 내가 만들었다.** `quote` 가 있는 dev 기준으로만 시험했고
`quote` 가 없는 경우를 생각하지 않았다.

빈 `quote` 를 `not_found` 로 처리하는 수정은 이미 들어가 있다.
그러나 **이미 파일에 박힌 값을 되돌릴 방법이 없었다.**

## 조치 — `--mode facts`

`expected_facts` 는 평가셋 작성자가 **원문을 보고 적은 문장**이므로 `quote` 와 같은 역할을 한다.
이것을 8글자 단위로 쪼개 근거 쪽의 청크 본문과 대조한다.

**검색을 쓰지 않는다.** `src/link_evidence.py` 는 색인도 벡터도 import 하지 않으므로
작성자가 직접 돌려도 같은 결과가 나온다. 순환이 아니다.

확신이 없으면 배정하지 않는다.

```
FACTS_MIN    = 0.20    겹침이 이 비율 미만이면 배정 안 함
FACTS_MARGIN = 3.0     2위의 이 배 미만이면 배정 안 함
```

틀린 값을 박아 "28건 다 있다" 로 보이게 한 것이 애초에 이 사고의 원인이므로,
모르는 것은 비워 둔다.

## 결과 (청크 1,815 기준)

```
근거 32건 (mode=facts)
  facts_ok     12
  facts_weak   20
  not_found     0
```

원본은 28건에 `chunk_id` 가 있으나 **그중 대부분이 위 버그의 산물**이다.

## 한계

- `expected_facts` 대조도 완전하지 않다. 1,881청크 시점에 7건을 고쳐 측정했을 때
  TEST-010 은 오히려 나빠졌다(4위 O -> 17위 X). 기계 대조의 한계다.
- `facts_weak` 20건은 여전히 미확정이다. 그 쪽에 답이 없을 가능성(쪽 번호 자체가 틀림)도 있다.
- **확정은 평가셋 작성자가 해야 한다.** 검색 담당이 정한 정답으로 검색 성능을 발표할 수 없다.

## 작성자께 요청

`facts_weak` 20건에 **원문 한 줄씩** (`quote`) 넣어주면 자동으로 확정된다.
dev 는 그 방식으로 36건 중 34건이 붙었다.

## 측정 (idx-v5, 청크 1,815, 구성 A, KURE-v1)

분모가 다르므로 **양쪽 다 채점된 12문항**만 비교한다.

```
           001 002 003 004 005 007 009 010 011 012 014 017
원본        O   X   X   X   X   O   O   O   X   X   O   X     5/12
facts       O   O   X   O   O   O   O   X   O   O   X   O     9/12
```

| 문항 | 원본 | facts | |
| --- | --- | --- | --- |
| TEST-002 | 7위 | **1위** | 개선 |
| TEST-004 | 20위 밖 | **2위** | 개선 |
| TEST-005 | 20위 밖 | **1위** | 개선 |
| TEST-011 | 20위 밖 | **1위** | 개선 |
| TEST-012 | 20위 밖 | **1위** | 개선 |
| TEST-017 | 7위 | **1위** | 개선 |
| TEST-010 | 4위 | 15위 | **악화** |
| TEST-014 | 1위 | 20위 밖 | **악화** |

전체 기준으로는 원본 8/16 (MRR 0.345), facts 9/12 (MRR 0.664).

### 읽는 법

**개선된 6건 중 5건이 1위로 들어왔다.** 정답을 고를 때 검색을 쓰지 않았는데
고친 정답이 1위에 있었다는 것은, 시스템이 처음부터 그 청크를 찾고 있었고
정답지가 다른 곳을 가리켜 틀림으로 집계됐다는 뜻이다.
원본에서 20위 밖이던 4건이 전부 1~2위가 된 것은 우연으로 보기 어렵다.

**그러나 2건은 내 보정이 틀렸다.** TEST-014 는 원본 정답이 1위였는데
겹침 기준을 넘겨 교체되는 바람에 20위 밖이 됐다. TEST-010 도 같다.
`expected_facts` 대조만으로는 확정할 수 없다는 증거다.

### 결론

- **확실한 것**: 정답지에 명백한 오류가 있다. 생성 경위(버그)가 코드로 설명되고,
  6건이 바로잡히면서 1~2위로 들어왔다.
- **불확실한 것**: 진짜 점수. 원본 5/12 도 내 보정 9/12 도 틀린 구석이 있다.

**`quote` 없이는 확정할 수 없다.** 검색 성능을 발표하려면 정답지부터 확정해야 한다.
