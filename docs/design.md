# 검색 설계 (design.md)

> 담당: 서종찬 (문서·색인 / 검색·재정렬)
> 평가표 **3번**(문서 처리·메타데이터), **4번**(하이브리드 검색), **5번**(re-ranking)의 증빙 문서.
> `[기입]`은 구현하면서 실제 값으로 채운다. 비워두면 평가 항목이 빈다.

## 1. 버전 고정

| 항목 | 값 | 확정일 |
|---|---|---|
| 문서 세트 버전 | `[기입]` | |
| 색인 버전 | idx-v2 (DOC-INTRO 추가, 1,653 청크) | |
| 임베딩 모델 | `nlpai-lab/KURE-v1` (1024차원, 로컬) | 2026-11-25 |
| Reranker 모델 | `BAAI/bge-reranker-v2-m3` (cross-encoder, 로컬) | 2026-11-25 |
| 평가셋 버전 | dev v1.0 / test v1.0 | |

## 2. 청킹 (평가표 3번)

| 항목 | 결정 | 근거 |
|---|---|---|
| 단위 | 조항 (`제N조 제M항`) | 법령에 이미 의미 경계가 있음 |
| 겹침(overlap) | 없음 | 조항이 완결된 의미 단위라 문맥이 잘리지 않음 |
| 조항이 너무 길 때 | `[기입]` | 임베딩 입력 한도 초과 시 항·호로 분할 |
| 분할 시 ID | `DOC-01#a046-1`, `-2` | |

### chunk_id 생성 규칙

- 방식: `[기입 — 위치 기반 / 내용 해시 중 선택]`
- **결정적이어야 한다.** 같은 입력을 두 번 돌리면 같은 ID가 나와야 `gold_chunks`가 유지된다.
- 검증: `chunks.jsonl`을 두 번 생성해 해시를 비교한 로그를 `results/`에 남긴다.

### 청크 스키마

```json
{
  "chunk_id": "DOC-01#a046-1",
  "doc_id": "DOC-01",
  "doc_title": "",
  "doc_version": "",
  "location": "제46조 제1항",
  "visa_codes": [],
  "effective_date": "",
  "index_version": "idx-v1",
  "text": ""
}
```

`chunk_id` / `doc_id` / `location` 세 개는 **없으면 색인 단계에서 에러로 막는다.** 출처를 못 대는 청크는 쓸 수 없다.

## 3. 토크나이징 (평가표 4번)

### 문제

1. 한국어는 교착어라 `비자를` ≠ `비자가` → 어휘 일치 실패
2. 형태소 분석기가 `E-7`을 `[E][7]`로 분해 → **코드 정확 일치가 붕괴**

### 처리 순서

1. 정규식으로 보호 토큰 추출 — 비자 코드 `[A-Z]-\d+`, 고시 번호, 양식 번호
2. 남은 텍스트만 Kiwi에 통과
3. 두 결과를 합쳐 BM25 입력 토큰 목록 구성

**질문과 문서에 동일한 전처리를 적용한다.** 한쪽만 보호하면 여전히 안 맞는다.

### 검증 실험

| 조건 | Hit@5 (dev 10문항) |
|---|---|
| 보호 규칙 off | `[기입]` |
| 보호 규칙 on | `[기입]` |

→ 평가표 4번 "결합 방법을 설명할 수 있는가"에 측정값으로 답하는 근거.

## 4. 검색 구성 (평가표 4번)

| 구성 | 내용 | 기록할 설정 |
|---|---|---|
| A | Vector 단독 | 임베딩 모델, k |
| B | BM25 + Vector, RRF 결합 | 각 검색기 후보 수, RRF k, 중복 제거 규칙 |
| C | B + re-ranking | reranker 모델, 입력 후보 수, 출력 k |

### 결합 방식: RRF

```
score(d) = 1/(60 + rank_bm25(d)) + 1/(60 + rank_vector(d))
```

**채택 근거** — BM25 점수는 상한이 없고(0~30대 이상) 코사인 유사도는 0~1이라 자릿수가 다르다. 단순 합산하면 BM25가 벡터를 압도한다. RRF는 점수를 버리고 순위만 쓰므로 정규화 가정 없이 결합할 수 있다.

| 설정 | 값 |
|---|---|
| BM25 후보 수 | 20 |
| Vector 후보 수 | 20 |
| RRF k | 60 (원논문 기본값) |
| 결합 후 상위 | `[기입]` |
| 중복 청크 처리 | 같은 chunk_id는 두 순위의 RRF 점수를 합산 |

> ⚠️ 라이브러리의 하이브리드 검색 함수 하나를 호출하지 않는다. BM25 검색과 벡터 검색을 **따로 호출하고 결합 로직을 직접** 가지고 있어야 평가표 4번의 "직접 구현"을 만족한다.

## 5. 재정렬 (평가표 5번)

| 항목 | 값 |
|---|---|
| 방식 | Cross-encoder (질문+청크를 한 쌍으로 입력) |
| 모델 | `BAAI/bge-reranker-v2-m3` — 다국어(한국어 포함), KURE-v1 과 같은 bge-m3 계열 |
| 입력 후보 수 | 20 |
| 출력 k | 5 — 프롬프트에 들어가는 상위 청크 수 (`[prompt] max_context_chunks`, A/B/C 공통) |
| 입력 텍스트 | 질문 + (절 경로 + 청크 본문), 최대 1024 토큰 (`max_length`) |
| 동점 처리 | 재정렬 전(RRF) 순위가 앞선 쪽 우선 |
| 기록 | 입력 20개 전부를 `rank_before_rerank` / `rank_after_rerank` 와 함께 반환·기록. 점수는 `component_scores` 에 `rerank`·`rrf`·`bm25`·`vector` 따로 |
| 시간 | `latency.rerank_ms` (검색 시간 `retrieval_ms` 와 분리) |
| 코드 | `src/rerank.py`, `src/search_adapter.py` (`hybrid_rerank`), `configs/C.toml` |

C 는 20개를 모두 돌려주고 프롬프트는 상위 5개만 쓴다. 그래야 기록만으로 "근거가 후보 20개에 아예 없었나(검색 누락)"와
"후보에는 있었는데 재정렬 후 5위 밖으로 밀렸나(순위 실패)"를 구분할 수 있다 (problem.md 11.4).

**RRF 점수로 다시 정렬하는 것은 재정렬이 아니다.** 관련도를 처음부터 다시 계산해야 한다.

모든 실행에 `before_rerank` / `after_rerank` 순위 배열을 저장한다. 혼동 축 문항에서 **순위가 실제로 바뀐 사례를 최소 1건** 확보한다.

## 6. 혼동 축 (문서 설계와 연결)

| 축 | 충돌 | 노리는 실패 |
|---|---|---|
| C1 | 전문인력 비자 ↔ 사내 전근 비자 | 요건이 유사해 벡터가 구분 못 함 |
| C2 | 비자 면제 ↔ 도착 비자 | 둘 다 "사전 비자 불필요"지만 조건이 다름 |
| C3 | 체류 연장 ↔ 자격 변경 | 절차·서류가 완전히 다름 |
| C4 | 정책 공지에 의한 규정 변경 | 구 규정과 신 공지가 동시 검색 |
