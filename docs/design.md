## 2. 청킹 (평가표 3번)

원문은 법령이 아니라 **행정 안내 매뉴얼**이다. 조문 번호가 없고 제목 계층으로만 구조가 잡혀 있다.
그래서 조항이 아니라 **제목 경로**를 의미 경계로 쓴다.

| 항목 | 결정 | 근거 |
|---|---|---|
| 단위 | 제목 경로 (`유학(D-2) > 체류기간 연장허가 > 다. 제출서류`) | 매뉴얼이 제목으로 사안을 나눈다 |
| 겹침(overlap) | 없음 | 제목 아래가 완결된 안내 단위라 문맥이 잘리지 않음 |
| 길이 상한 | 1,200자 (`MAXLEN`). 넘으면 **줄 경계**로 분할 | 문장 중간이 잘리지 않게 |
| 실제 분포 | 평균 348자, 최대 1,285자 | 상한 근처까지 가는 청크는 드물다 |
| 분할된 조각 | 298개 (`n_parts > 1`) | `section_key` 로 묶어 프롬프트에서 재조립 (11절) |
| 청크 종류 | `body` 1,636 / `fold` 179 | `fold` 는 본문 없는 제목만 있는 절 |

### chunk_id 생성 규칙

**내용 해시 방식**을 쓴다.

```python
key = f'{doc_id}|{">".join(path)}|{seq}|{text[:200]}'
chunk_id = f"{doc_id}#{sha1(key).hexdigest()[:10]}"
```

| 구성요소 | 왜 넣었나 |
|---|---|
| `doc_id` | 문서 간 충돌 방지. ID 를 보면 어느 비자 문서인지 바로 안다 |
| 제목 경로 | 같은 문서 안의 절을 구분 |
| `seq` | **같은 경로가 문서 안에 여러 번 나오기 때문.** F-4 자격부여 요건이 p.601 과 p.618 에 같은 제목·같은 문장으로 실려 있다. seq 없이는 두 청크가 같은 ID 를 받아 평가셋이 어느 쪽을 가리키는지 알 수 없다 |
| `text[:200]` | 내용이 바뀌면 ID 도 바뀌어야 한다 |

- **결정적이어야 한다.** 같은 입력을 두 번 돌리면 같은 ID 가 나와야 평가셋의 `chunk_id` 가 유지된다.
  UUID 등 난수는 쓰지 않는다.
- 실제로 이 규칙을 세우기 전 **충돌이 2건** 났고, `seq` 를 넣어 해결했다 (`docs/conversion_notes.md` 수정 7).

### 청크 스키마

```json
{
  "chunk_id": "DOC-A1#64ef6a046d",
  "doc_id": "DOC-A1",
  "doc_title": "외교(A-1)",
  "doc_version": "2026-11-16",
  "source": "법무부 출입국·외국인정책본부 「체류민원 자격별 안내 매뉴얼」",
  "location": "외교(A-1) > 체류자격 변경허가 > 1. 법적 혼인관계의 배우자",
  "page": 16,
  "visa_codes": ["A-1"],
  "chunk_kind": "body",
  "section_key": "fdc4205f6d",
  "part": 1,
  "n_parts": 1,
  "text": "..."
}
```

`chunk_id` / `doc_id` / `location` / `page` 네 개는 **없으면 색인 단계에서 에러로 막는다.**
출처를 못 대는 청크는 인용을 달 수 없어 쓸 수 없다.

## 3. 토크나이징 (평가표 4번)

### 문제

1. 한국어는 교착어라 `비자를` ≠ `비자가` → 어휘 일치 실패
2. 형태소 분석기가 `E-7` 을 `[E][-][7]` 로 분해 → **비자 코드 정확 일치가 붕괴**

### 처리 순서 (`src/tokenizer.py`)

```python
VISA_CODE = r"[A-Za-z]-\d+(?:-\d+)?"
KEEP = ("NN", "VV", "VA", "SL", "SN")
```

1. 정규식으로 비자 코드를 먼저 추출해 대문자로 보관하고, 원문에서 지운다
2. 남은 텍스트만 Kiwi 에 통과시켜 명사·동사·형용사·외국어·숫자만 남긴다
3. 두 결과를 합쳐 BM25 입력 토큰으로 쓴다

**질문과 문서에 동일한 전처리를 적용한다.** 한쪽만 보호하면 여전히 안 맞는다.
형태소 분석기는 `kiwipiepy` 를 쓴다 — 순수 파이썬 휠이라 JVM 설치가 필요 없고, 팀원 전원이 같은 환경을 만들 수 있다.

### 검증 실험

| 조건 | dev Hit@5 | dev MRR | test Hit@5 | test MRR |
|---|---|---|---|---|
| 보호 규칙 off | `[측정 예정]` | | | |
| 보호 규칙 on | `[측정 예정]` | | | |

BM25 단독 구성으로 비교한다. 벡터 검색은 토크나이저를 쓰지 않으므로 영향을 받지 않는다.

## 4. 검색 구성 (평가표 4번)

| 구성 | 내용 | 설정 |
|---|---|---|
| A | Vector 단독 | `nlpai-lab/KURE-v1`, 후보 20, 상위 5 |
| B | BM25 + Vector, RRF 결합 | 각 20 후보, RRF k=60, 상위 5 |
| C | B + re-ranking | `BAAI/bge-reranker-v2-m3`, 입력 20, 출력 5 |

### 결합 방식: RRF (직접 구현)

```
score(d) = Σ wᵢ / (k + rankᵢ(d))        k = 60
```

**채택 근거** — BM25 점수는 상한이 없고(0~30대 이상) 코사인 유사도는 0~1 이라 자릿수가 다르다.
단순 합산하면 BM25 가 벡터를 압도한다. RRF 는 점수를 버리고 순위만 쓰므로 정규화 가정 없이 결합할 수 있다.

| 설정 | 값 |
|---|---|
| BM25 후보 수 | 20 |
| Vector 후보 수 | 20 |
| RRF k | 60 (원논문 기본값) |
| 가중치 | `w_bm25` 조정 가능 (기본 1.0) |
| 결합 후 상위 | **5** (Hit@5 와 맞춤, `[prompt] max_context_chunks` 와 동일) |
| 중복 청크 처리 | 같은 `chunk_id` 는 두 순위의 RRF 점수를 합산 |

라이브러리의 하이브리드 검색 함수를 호출하지 않는다. BM25 검색과 벡터 검색을 따로 호출하고
결합 로직(`src/retrieve.py` 의 `rrf()`)을 직접 가지고 있다.

### 측정 결과 — 구성 B 를 채택하지 않는다

| 구성 | dev Hit@5 | dev MRR | test Hit@5 | test MRR |
|---|---|---|---|---|
| BM25 단독 | 3/8 | 0.391 | 9/17 | 0.445 |
| **A 벡터 단독** | **8/8** | **0.792** | **15/17** | **0.774** |
| B 혼합 w=1.0 | 7/8 | 0.597 | 13/17 | 0.679 |
| B 혼합 w=0.5 | 7/8 | 0.766 | — | — |
| B 혼합 w=0.3 | 7/8 | 0.745 | — | — |

**BM25 의 적중은 벡터 적중의 부분집합이다.** test 에서 BM25 가 맞힌 9문항이 모두 벡터 적중 15문항에
포함된다. 벡터가 놓친 TEST-003·TEST-013 은 BM25 도 못 찾는다. 즉 추가로 건지는 것이 없고,
잘 찾던 것을 밀어내기만 한다.

**원인**은 코퍼스 구조로 본다. 39개 문서가 모두 같은 절 구조(제출서류 / 허가기준 / 신청요령 /
체류기간 연장허가)를 가져서, "체류기간 연장허가 제출서류" 같은 질의는 전 문서에 걸린다.
어휘에 변별력이 없다. 벡터는 "D-4 어학연수생" 이라는 맥락을 반영해 해당 문서를 집어낸다.

RRF 는 점수를 버리는 대신 **검색기의 품질 차이도 함께 버린다.** 품질이 2배 차이나는 두 검색기를
동등 가중으로 합치면 약한 쪽으로 끌려간다. w=0.5, 0.3 으로 낮춰도 A 를 넘지 못했다.

> 가중치 조정은 dev 에서만 했다. test 로 손잡이를 돌리면 과적합이다.
> dev 8문항에서 0.766 과 0.745 의 차이는 신뢰하지 않는다 — 한 문항이 한 칸 움직이면 그만큼 흔들린다.
> 신뢰하는 것은 "A 가 모든 B 변형보다 높다" 와 "dev 와 test 가 같은 결론" 두 가지다.

상세: `results/runs/2026-11-26_bm25-vs-vector.md`

> **단, 재정렬 앞단으로서의 B 는 아직 판단하지 않았다.** 재정렬은 후보를 다시 줄 세우는 것이므로
> 앞단에서 중요한 것은 상위 5 순서가 아니라 **후보 20개 안에 정답이 있는 비율(Hit@20)** 이다.
> 이 값을 재기 전에는 구성 C 의 후보 생성기를 A 로 할지 B 로 할지 정할 수 없다.

## 5. 재정렬 (평가표 5번)

| 항목 | 값 |
|---|---|
| 방식 | Cross-encoder (질문+청크를 한 쌍으로 입력) |
| 모델 | `BAAI/bge-reranker-v2-m3` — 다국어(한국어 포함), KURE-v1 과 같은 bge-m3 계열 |
| 입력 후보 수 | 20 |
| 출력 k | 5 — 프롬프트에 들어가는 상위 청크 수 (`[prompt] max_context_chunks`, A/B/C 공통) |
| 입력 텍스트 | 질문 + (절 경로 + 청크 본문), 최대 1024 토큰 (`max_length`) |
| 동점 처리 | 재정렬 전(RRF) 순위가 앞선 쪽 우선 |
| 기록 | 입력 20개 전부를 `rank_before_rerank` / `rank_after_rerank` 와 함께 반환·기록. 점수는 `component_scores` 에 `rerank`·`rrf`·`bm25`·`vector` 따로 |
| 시간 | `latency.rerank_ms` (검색 시간 `retrieval_ms` 와 분리) |
| 코드 | `src/rerank.py`, `src/search_adapter.py` (`hybrid_rerank`), `configs/C.toml` |

C 는 20개를 모두 돌려주고 프롬프트는 상위 5개만 쓴다. 그래야 기록만으로 "근거가 후보 20개에 아예 없었나(검색 누락)"와
"후보에는 있었는데 재정렬 후 5위 밖으로 밀렸나(순위 실패)"를 구분할 수 있다 (problem.md 11.4).

**RRF 점수로 다시 정렬하는 것은 재정렬이 아니다.** 관련도를 처음부터 다시 계산해야 한다.

모든 실행에 `before_rerank` / `after_rerank` 순위 배열을 저장한다. 혼동 축 문항에서 **순위가 실제로 바뀐 사례를 최소 1건** 확보한다.

## 6. 혼동 축 (문서 설계와 연결)

| 축 | 충돌 | 노리는 실패 |
|---|---|---|
| C1 | 전문인력 비자 ↔ 사내 전근 비자 | 요건이 유사해 벡터가 구분 못 함 |
| C2 | 비자 면제 ↔ 도착 비자 | 둘 다 "사전 비자 불필요"지만 조건이 다름 |
| C3 | 체류 연장 ↔ 자격 변경 | 절차·서류가 완전히 다름 |
| C4 | 정책 공지에 의한 규정 변경 | 구 규정과 신 공지가 동시 검색 |

## 11. 섹션 확장 (2026-11-26)

**배경**: 1,200자를 넘는 항목은 `src/ingest/chunk.py`에서 연속된 조각으로 분할된다. 128개 항목이 300개 조각 쌍을 이루며, 검색이 조각 하나만 반환하면 모델이 목록을 절반만 본다. dev 세트에서 DEV-001·005·006이 이 문제를 직접 보여 준다.

**결정**: 검색 단위·순위는 그대로 두고, 프롬프트를 구성할 때만 선택된 청크를 해당 절 전체(모든 조각, 순서대로)로 대체한다.

**섹션 식별**: `chunk.py`의 `emit_body`에서 각 청크에 세 필드를 추가한다.

| 필드 | 설명 |
|---|---|
| `section_key` | 절 단위 고유 키. `sha1("{doc_id}|{loc}|{occurrence}")[:10]` |
| `part` | 이 절 안에서의 순번 (1-based) |
| `n_parts` | 이 절의 전체 조각 수 |

`location`에서 ` (n)` 접미사를 제거하는 방식을 쓰지 않는다. 같은 경로가 문서 안에서 여러 번 등장할 때(예: F-4 자격부여 요건 p.601·p.618) `occurrence`가 달라 다른 키를 받으므로 잘못 합쳐지지 않는다.

**설정** (`[prompt]` in `configs/base.toml`):

| 키 | 값 | 근거 |
|---|---|---|
| `expand_sections` | `true` | 섹션 확장 on/off |
| `max_expanded_chars` | `20000` | 128절 × 평균 3.3조각 × 1,200자 ≈ 최대 조각당 3,960자 × 5 청크 ≒ 19,800자에서 역산. dev 전용 결정. |

**예산 규칙**: 순위 높은 절부터 확장; 한도를 넘으면 하위 절은 원래 조각 그대로 둔다. 검색된 청크는 절대 삭제하지 않는다.

**인용 규칙**: 프롬프트의 `<document chunk_id="...">` 는 검색된 조각의 ID를 쓴다. `expanded_from="id1,id2"` 속성으로 실제 포함된 조각을 기록한다. `check_citations`는 검색된 ID만 허용하는 기존 규칙을 유지한다.

**검증 범위**: dev 세트 한정으로 결정. eval 동결 전 테스트 세트 열람 없음.
