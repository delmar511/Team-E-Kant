## 2. 청킹 (평가표 3번)

### 2.1 단위

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 단위 | 제목 계층의 최하위 (`#### 가./나./다.`) | 매뉴얼이 업무 구분 > 번호 > 가나다 로 이미 의미를 나눠 놓았다 |
| `####` 가 없는 구간 | `###` 또는 `##` 로 올림 | |
| 겹침(overlap) | **없음** | 제목 단위가 완결된 의미 단위라 문맥이 잘리지 않는다 |
| 최대 길이 | 1,200자 초과 시 문단 경계로 분할 | 실측 최대 1,285자 |
| 상위 제목 | 버리지 않고 `location` 으로 보존 | 인용 시 사람이 원문을 찾을 수 있어야 한다 |

원문이 **2단 표**라 왼쪽 열(업무 구분)이 오른쪽 본문 사이사이에 끼어 있다.
이를 제목 계층으로 복원하는 전처리를 거쳤다. 규칙과 수정 이력은 `docs/conversion_notes.md`.

### 2.2 주소 3종

모든 청크가 세 가지를 반드시 가진다. 없으면 색인 단계에서 에러를 낸다
(`src/build_index.py` 의 `load_chunks`).

| 필드 | 예 | 용도 |
| --- | --- | --- |
| `chunk_id` | `DOC-D2#94bd3000d6` | 평가 채점 (`gold_chunks`) |
| `doc_id` | `DOC-D2` | 문서 단위 집계 |
| `location` | `유학(D-2) > 체류기간 연장허가 > 다. 제출서류` | 사용자 인용 |

이 밖에 `doc_title`, `doc_version`, `source`, `page`, `visa_codes` 를 함께 저장한다.

### 2.3 chunk_id 를 결정적으로 만든 이유

```python
key = f'{doc_id}|{">".join(path)}|{seq}|{text[:200]}'
chunk_id = f'{doc_id}#{sha1(key)[:10]}'
```

랜덤 UUID 를 쓰면 재색인할 때마다 ID 가 바뀌어 평가셋의 `gold_chunks` 가 깨진다.
같은 입력이면 같은 ID 가 나오도록 해시로 만든다.

`seq`(문서 내 같은 경로의 등장 순번)를 넣은 이유: 매뉴얼이 같은 내용을 두 곳에
반복 수록하는 구간이 있어, 그것을 넣지 않으면 서로 다른 청크가 같은 ID 를 받는다
(실제로 2건 발생해 수정).

### 2.4 코퍼스 범위를 좁히지 않은 이유

평가 대상은 D-2·D-4 두 자격이지만 36개 문서를 모두 넣었다.

좁히면 점수는 오른다. 실제로 `제출서류` 같은 흔한 항목명에서 다른 자격이 경쟁자로
올라와 BM25 검색을 방해한다(`results/runs/2026-11-25_bm25-baseline.md`).

그러나 **평가셋에 맞춰 문서를 고르는 것**이 되어 실제 사용 환경과 멀어진다.
사용자는 어느 자격을 물을지 모르는 상태로 질문한다. 좁히지 않고 검색으로 푼다.

## 3. 토크나이저 (평가표 3·4번)

### 3.1 형태소 분석을 쓴 이유

띄어쓰기로 자르면 `유학생이` 와 `유학생` 이 다른 단어가 된다.
한국어는 조사·어미가 붙어 같은 말이 계속 다르게 보인다.

`kiwipiepy` 를 선택했다. **순수 파이썬 휠이라 JVM 이 필요 없다.**
팀원 전원이 설치해야 하므로 설치 부담이 선택 기준이었다.
남기는 품사는 `NN*`(명사), `VV`(동사), `VA`(형용사), `SL`(외국어), `SN`(숫자).

### 3.2 비자 코드 보호

`E-7` 을 형태소 분석기에 넣으면 `E` / `-` / `7` 로 쪼개진다.
숫자 `7` 은 `제7조`, `7일` 과도 겹쳐 엉뚱한 문서가 걸린다.

그래서 **형태소 분석 전에** 정규식 `[A-Za-z]-\d+(?:-\d+)?` 으로 코드를 먼저 빼내고,
나머지만 분석한 뒤 합친다. 소문자 입력(`e-7`)은 대문자로 정규화한다.

보호 ON/OFF 비교에서, OFF 일 때 숫자 `7` 이 무관한 문서와 매칭되어
틀린 문서가 1위로 올라오는 것을 확인했다.

## 4. 검색 구성 (평가표 4번)

### 4.1 구성 정의

| 구성 | 내용 | 구현 |
| --- | --- | --- |
| A | 벡터 단독 | `search_vector()` |
| B | BM25 + 벡터, RRF 결합 | `rrf(search_bm25(), search_vector())` |
| C | B 의 후보를 재정렬 | **미구현** |

각 검색기가 후보 20개를 내고, 결합 후 상위 5개를 반환한다(Hit@5 와 맞춤).

### 4.2 RRF 를 직접 구현한 이유

```python
score(d) = Σ  w_i / (k + rank_i(d))
```

점수를 그냥 더하면 안 된다. BM25 는 상한이 없고(실측 8~18) 코사인은 0~1 이라
BM25 가 벡터를 압도한다. 발제도 단순 합산을 금지한다.

RRF 는 점수를 버리고 **순위만** 쓴다. 양쪽에서 모두 뽑힌 문서가 두 번 점수를 받아
위로 올라간다. 라이브러리의 하이브리드 함수를 호출하지 않고 이 결합을 직접 가지고 있다.

### 4.3 가중치를 추가한 이유

동등 가중치 RRF 는 **두 검색기의 품질이 비슷할 때를 가정한다.**

`k=60` 에서 1위(`1/61`)와 2위(`1/62`)의 차이는 1.6% 뿐이다.
반면 검색기 간 품질 차이는 MRR 0.792 대 0.453 으로 크다.
그 결과 약한 검색기의 1·2위가 강한 검색기의 1위와 사실상 동점이 되어 앞자리를 차지한다.

검색기별 가중치 `w_i` 를 두어 기여도를 조절할 수 있게 했다. 전부 1.0 이면 원래 RRF 와 같다.

## 5. 임베딩 모델 선택 (평가표 4번)

원본: `results/runs/2026-11-25_embedding-compare.md`

구성 A(벡터 단독)로 비교했다. 구성 B 는 BM25 가 섞여 모델 차이를 가린다.
Hit@5 외에 **정답 청크의 순위와 MRR** 을 같이 봤다. 문항이 8개뿐이라
Hit@5 의 해상도로는 모델 간 차이를 판단할 수 없기 때문이다.

| 모델 | 차원 | Hit@5 | MRR |
| --- | --- | --- | --- |
| `text-embedding-3-small` | 1536 | 6/8 | 0.427 |
| `text-embedding-3-large` | 3072 | 7/8 | 0.701 |
| `BAAI/bge-m3` | 1024 | 8/8 | 0.754 |
| **`nlpai-lab/KURE-v1`** | 1024 | **8/8** | **0.792** |

**관찰**

- 차원은 성능을 결정하지 않는다. 1024차원이 3072차원을 모든 문항에서 이겼다.
- 한국어 추가 학습의 효과가 확인된다. KURE-v1 은 bge-m3 를 한국어로 추가 학습한 모델이고,
  **뼈대가 같고 학습만 다른 쌍**에서 0.754 → 0.792 로 올랐다.
  공개 벤치마크(MTEB-ko)의 순서와도 일치한다.

**비용**

| | KURE-v1 | OpenAI 3-large |
| --- | --- | --- |
| 전량 임베딩(1,646개) | 5분 36초 (CPU) | 13.8초 |
| 설치 | PyTorch 포함 2~3GB | 없음 |
| 모델 내려받기 | 약 2.2GB | 없음 |
| 비용 | 0 | 약 $0.1 |

성능은 KURE 가 낫지만 팀원 전원이 설치해야 한다. **최종 선택은 팀 합의 사항.**

## 6. 측정 결과 (dev, 8문항)

| 구성 | 임베딩 | Hit@5 | MRR |
| --- | --- | --- | --- |
| BM25 단독 | - | 4/8 | 0.453 |
| A (벡터 단독) | 3-large | 7/8 | 0.701 |
| B (RRF, w=1.0) | 3-large | **8/8** | - |
| A (벡터 단독) | KURE-v1 | **8/8** | **0.792** |
| B (RRF, w=1.0) | KURE-v1 | 7/8 | 0.557 |
| B (RRF, w=0.1) | KURE-v1 | 8/8 | 0.646 |

### 하이브리드가 항상 낫지는 않았다

**같은 코드에서 임베딩 모델만 바꾸자 BM25 의 역할이 반대로 뒤집혔다.**

| 벡터 모델 | 구성 A | 구성 B | BM25 |
| --- | --- | --- | --- |
| OpenAI 3-large | 7/8 | **8/8** | 도움 |
| KURE-v1 | **8/8** | 7/8 | 방해 |

하이브리드의 이득은 **두 검색기의 품질 격차**에 달려 있다.
격차가 작으면 서로 보완하고, 크면 약한 쪽이 강한 쪽을 끌어내린다.

`w_bm25` 를 0.1 까지 낮춰도 벡터 단독(0.792)을 넘지 못했다
(`results/runs/2026-11-25_rrf-weight-sweep.md`).

### 그러나 BM25 를 버리지 않는다

DEV-006 (`D-2-2` 와 `D-2-3` **각각의** 허용 시간)은 BM25 만 1위로 찾는다.
보호 토큰이 코드를 한 덩어리로 지키기 때문이다.
벡터는 OpenAI 든 KURE 든 이 문항에서 1위를 내지 못했다.

dev 에는 그런 문항이 하나뿐이라 손실이 더 크지만,
test 20문항은 `direct` 10 + `confusable` 4 로 비율이 다르다. **결론이 뒤집힐 수 있다.**

## 8. 알려진 한계

`docs/conversion_notes.md` 의 L1~L8 참조. 검색과 직접 관련된 것만 옮긴다.

- **본문 배정이 추정이다.** 2단 표의 실제 괘선을 읽는 것이 아니라 제목 위치로 구간을 나눈다.
  한 항목의 본문이 다음 항목명 시작선을 넘으면 잘못 배정될 수 있다. (L5)
- **표를 Markdown 표로 복원하지 않는다.** 행 단위 텍스트로 남긴다.
  여러 행에 걸친 묶음 라벨(`학위과정 (D-2)`)은 해당 행에만 붙는다. (L6)
- **본문 없는 제목은 청크가 되지 않는다.** 평가셋이 그런 제목을 근거로 지목하면
  `chunk_id` 를 채울 수 없다. (L8)
- **평가셋의 `section` 은 자유 형식**이라 `location` 과 글자 그대로 맞지 않는다.
  `chunk_id` 는 `quote` 를 본문에서 찾아 채운다 (`src/link_evidence.py`). (L7)

## 9. 재현 절차

```bash
pip install -r requirements.txt
pip install sentence-transformers          # KURE 를 쓸 경우

# .env 에 OPENAI_API_KEY, EMBEDDING_MODEL 설정

pdftotext -layout 매뉴얼.pdf cheryu.txt     # poppler 필요
python src/ingest/batch_convert.py cheryu.txt docs/corpus
python src/ingest/chunk.py "docs/corpus/*.md" > data/chunks.jsonl
python src/build_index.py
python src/build_vectors.py

python src/retrieve.py --config A --eval eval/eval-dev.json
python src/compare_embeddings.py <모델명> <모델명> ...
```

`docs/corpus/` 와 `data/chunks.jsonl` 은 레포에 있으므로 PDF 변환은 건너뛸 수 있다.
