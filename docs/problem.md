# 문제 정의: 출입국 체류민원 정책 확인용 Knowledge Agent

> 작성 상태: 초안 (팀 검토 필요)
> 기준 확정일: YYYY-MM-DD (최종 평가 실행 전 커밋으로 고정)
> 대상 문서 버전: 하이코리아 「체류민원 자격별 안내 매뉴얼」 YYMMDD 판 (수집 시 기입)
>
> **미확정 항목 (커밋 전 기입)**
> - [ ] 매뉴얼 판(개정일자)·수집일 기입 (상단, 7절)

---

## 1. 한 줄 요약

출입국·외국인관서의 체류민원 담당자가 **D-2(유학)·D-4(일반연수)** 관련 신청을 처리할 때, 수백 쪽 분량의 공개 매뉴얼에서 요건·제출서류·예외 조건을 빠르게 찾고, **원문 위치를 확인할 수 있는 근거와 함께** 답을 얻거나 근거가 없으면 "문서에 근거 없음"을 안내받도록 돕는 RAG 기반 Knowledge Agent를 만든다.

---

## 2. 사용자

| 구분 | 내용 |
| --- | --- |
| 주 사용자 | 지방 출입국·외국인관서 체류민원 담당 공무원 (창구 접수·심사 담당) |
| 보조 사용자 | 순환 보직 등으로 새로 배치된 담당자, 민원 상담 응대 인력 |
| 사용 시점 | 민원 접수·심사 중 요건이나 제출서류를 확인해야 할 때, 민원인 문의에 답해야 할 때 |
| 다루는 업무 | 국내 체류 중인 외국인의 체류기간 연장, 체류자격 변경, 체류자격 외 활동(시간제취업) 허가, 근무처·학교 관련 변경 등 |
| 평가 집중 범위 | D-2(유학), D-4(일반연수) |

> 참고: 실제 공무원 내부 업무 환경을 재현하지 않으며, 일반에 공개된 매뉴얼과 법령을 대리 데이터로 사용한다. (8절 제외 범위 참조)

## 3. 기존 탐색 과정 (As-is)

### 3.1 업무 흐름

```
민원 접수 (연장/변경/시간제취업 등)
   │
   ▼
해당 체류자격 확인 (예: D-2-2, D-4-1)
   │
   ▼
매뉴얼 PDF/HWP 열기 → 목차 이동 또는 Ctrl+F 키워드 검색
   │
   ├─ 찾음 → 세부 요건·제출서류·예외 조항 확인
   │            │
   │            ▼
   │      관련 항목(공통 규정, 변경 대상 자격, 활동 허가 규정 등)을
   │      매뉴얼 안에서 추가로 찾아 대조
   │
   └─ 못 찾음 / 해석이 애매함
                │
                ▼
          선임자·동료에게 문의, 또는 과거 처리 사례 기억에 의존
   │
   ▼
민원인에게 요건·보완서류 안내 / 심사 진행
```

### 3.2 정보가 방대하고 서로 연결되어 있음

담당자가 참고하는 기준은 「체류민원 자격별 안내 매뉴얼」로 정리되어 있다. 문제는 출처가 흩어져 있는 것이 아니라, 하나의 매뉴얼이 수백 쪽 분량이고 그 안의 규정들이 서로 영향을 주어 **한 곳만 보고는 정확히 해석할 수 없다**는 점이다.

| 연결 유형 | 설명 |
| --- | --- |
| 공통 규정 → 자격별 규정 | 모든 자격에 적용되는 공통 제출서류·절차가 자격별 항목과 함께 적용됨 |
| 자격 간 참조 | 자격 변경(예: D-4 → D-2) 시 변경 대상 자격의 요건을 함께 확인해야 함 |
| 활동 허가 규정 → 자격 | 시간제취업 등 체류자격외활동 관련 규정을 자격별 항목과 함께 해석해야 함 |
| 세부약호별 차이 | 같은 자격 안에서도 세부약호(D-2-2, D-4-1 등)에 따라 조건이 달라짐 |
| 개정 | 한 항목의 개정이 관련 항목의 해석에 영향을 줌 |

> 위 연결 유형의 구체적 사례는 수집한 매뉴얼 판에서 원문 위치를 확인한 뒤 평가셋에 반영한다.

## 4. 탐색상의 문제

1. **분량과 구조**: 매뉴얼이 수백 쪽이고 체류자격·세부약호별로 비슷한 구조(대상 → 요건 → 제출서류)가 반복되어, 키워드 검색 시 다른 자격의 유사 항목이 함께 걸린다.
2. **유사 조건 혼동**: D-2와 D-4는 연장, 시간제취업, 학교 변경 등 같은 이름의 업무가 존재하지만 허용 조건·제출서류·예외가 다르다. 세부약호(예: D-2-2 학사과정, D-4-1 어학연수)에 따라서도 달라진다.
3. **표현 불일치**: 민원인과 담당자가 쓰는 말("아르바이트", "알바 허가")과 매뉴얼 용어("체류자격외활동허가", "시간제취업")가 달라 단순 키워드 검색이 실패한다.
4. **여러 위치를 함께 봐야 함**: 하나의 질문에 답하려면 공통 규정, 자격별 항목, 활동 허가 규정 등 매뉴얼의 여러 위치를 함께 확인해야 하며, 한 곳만 보면 오답이 될 수 있다.
5. **예외·단서 조항 누락 위험**: 핵심 요건은 찾아도 표 아래 비고, "다만 ~한 경우" 같은 단서 조항을 놓치기 쉽다.
6. **잦은 개정**: 매뉴얼이 지침 변경에 따라 연중 수시로 개정되어, 기억이나 이전 판에 의존하면 낡은 기준으로 안내할 수 있다.
7. **담당자 간 편차**: 애매한 경우 개인 경험이나 동료 문의에 의존하므로 관서·담당자마다 안내가 달라질 수 있다.

> 개선 전 업무 소요시간은 측정하지 않았다. 따라서 이 프로젝트는 **시간 절감률을 성과로 주장하지 않으며**, 검색·답변 품질과 응답 시간만 측정한다.

## 5. 오답·근거 부족의 영향

| 오류 유형 | 예시 | 영향 |
| --- | --- | --- |
| 잘못된 요건 안내 | 해당 자격에 없는 조건을 요구하거나, 필요한 조건을 빠뜨림 | 부당한 불허 또는 부적격자 허가 → 행정 신뢰 저하, 이의신청·행정소송 위험 |
| 제출서류 누락·과다 안내 | D-4 서류 목록을 D-2 신청인에게 안내 | 민원인 재방문, 처리 지연 |
| 기한 관련 오안내 | 연장 가능 시점, 변경 신고 기한 등을 잘못 안내 | 민원인이 의도치 않게 체류기간을 넘겨 불법체류·과태료 대상이 될 수 있음 |
| 낡은 기준 적용 | 개정 전 기준으로 안내 | 위와 동일, 관서 간 처리 불일치 |
| 근거 없는 단정 | 매뉴얼에 없는 내용을 그럴듯하게 생성 | 담당자가 AI 답변을 사실로 오인하여 처분에 반영할 위험. **가장 피해야 할 오류** |

**설계 원칙**: 이 업무에서는 "모른다"보다 "틀린 확신"이 더 위험하다. 따라서 근거가 부족하면 답변 대신 **정보 부족 안내**를 하고, 모든 답변에는 담당자가 직접 원문을 확인할 수 있도록 **문서·절·쪽 위치**를 함께 제시한다.

## 6. RAG를 선택한 이유

| 대안 | 한계 | RAG의 장점 |
| --- | --- | --- |
| 기존 방식 (PDF + Ctrl+F) | 용어가 다르면 못 찾음, 유사 항목이 섞여 나옴 | 의미 기반(Vector) 검색으로 표현 차이 보완, BM25로 정확한 용어·약호 매칭 유지 |
| 범용 LLM에 직접 질문 | 학습 시점 이후 개정 내용을 모름, 출처 확인 불가, 그럴듯한 오답 | 최신 판 매뉴얼을 색인하여 답변, 실제 검색된 청크를 출처로 제시 |
| 모델 파인튜닝 | 매뉴얼이 수시 개정되어 재학습 부담, 근거 추적 어려움 | 문서 교체 후 색인만 재생성하면 반영 |
| 규칙 기반 FAQ 챗봇 | 질문 형태가 다양해 규칙 유지가 어려움 | 자연어 질문 처리, 문서에 없으면 "근거 없음" 판정 가능 |

**하이브리드 검색이 필요한 이유**: 이 도메인은 `D-2-2`, `D-4-1`, `시간제취업` 같은 **정확한 약호·용어**(BM25에 유리)와, "알바 허가 받으려면?" 같은 **구어체 질문**(Vector에 유리)이 함께 쓰인다.

**re-ranking이 필요한 이유**: 매뉴얼 전체를 색인하면 D-2와 D-4, 다른 자격의 "연장 제출서류" 청크가 비슷한 점수로 함께 검색된다. 질문의 체류자격·업무 종류와 실제로 맞는 청크를 상위로 올리는 재평가 단계가 필요하다.

**여러 근거를 함께 제시하는 이유**: 매뉴얼의 규정이 서로 연결되어 있으므로(3.2절), RAG는 관련된 여러 청크(예: 자격별 항목과 공통 규정)를 함께 검색해 답변하고 각각의 출처를 제시한다. 다중 근거 중 일부가 누락된 경우는 실패 분석에서 별도로 다룬다.

## 7. 데이터 범위

| 구분 | 내용 |
| --- | --- |
| 색인 대상 (검색 범위) | 「체류민원 자격별 안내 매뉴얼」 **전체** (모든 체류자격). 함께 배포되는 「수정 이력」은 색인하지 않고 판 확인·버전 기록용으로만 사용 |
| 매뉴얼만 사용하는 이유 | 담당자가 실제 업무에서 참고하는 기준이 매뉴얼이며, 제출서류·요건·예외 등 질문의 답이 매뉴얼에 있다. 법령은 표현이 추상적이고 매뉴얼과 용어가 달라 검색 잡음이 될 수 있다. |
| 문서 단위 (`doc_id`) | 매뉴얼을 목차의 **장 단위로 나누어 장마다 별도 `doc_id`**를 부여한다. 혼동 용어·예외 조건을 포함한 문서가 2개 이상이어야 한다는 요건은, D-2·D-4 장과 이와 유사한 항목(연장, 변경, 체류자격외활동 등)을 가진 다른 장이 각각 별도 문서가 되는 것으로 충족한다. 장 경계와 `doc_id` 목록은 `docs/documents.csv`를 따르며, 정답표의 `evidence.doc_id`도 이 장 단위 ID를 쓴다. |
| 평가 대상 (질문 범위) | **D-2, D-4** 관련 질문만 출제 |
| 이렇게 나눈 이유 | 전체 매뉴얼을 색인하면 다른 자격의 유사 항목이 실제 업무처럼 **혼동 요소**로 작용하여 검색 성능 비교가 의미 있어진다. 평가는 30문항의 정답·근거를 직접 검증할 수 있는 범위로 좁힌다. |
| 데이터 성격 | 모두 일반에 공개된 공공 문서. 개인정보 없음 |
| 이용 조건 | 문서별 공공누리 유형을 문서 목록에 기록 (비상업적 학습 목적 사용, 출처 표시) |
| 버전 관리 | 매뉴얼 판(개정일자)과 수집일을 기록하고, 최종 평가 전 문서·청크·정답표 버전을 고정 |

## 8. 제외 범위

| 제외 항목 | 이유 |
| --- | --- |
| 사증발급(재외공관) 업무, 「사증민원 자격별 안내 매뉴얼」 | 국내 체류민원으로 범위 한정 |
| 허가·불허 판정 | 시스템은 **참고 정보 제공**만 하며 최종 판단은 담당자가 한다 |
| 실제 민원인 정보, 개별 사건 처리 | 개인정보 처리 금지, 공개·가상 데이터만 사용 |
| 출입국관리법·시행령·시행규칙 원문, 법무부 공지·보도자료 | 매뉴얼만 색인. 법적 근거는 법령에 있으나 시스템은 매뉴얼 내용으로만 답하며, 매뉴얼에 아직 반영되지 않은 신규 공지는 다루지 못함을 한계로 명시 |
| 비공개 내부 심사지침 | 공개 문서만 사용. 실제 현장에서는 내부 지침이 추가로 적용될 수 있음을 한계로 명시 |
| 문서에 없는 법률 해석·판례 판단 | 문서 근거 밖의 해석은 답하지 않고 정보 부족으로 안내 |
| 출입국 업무 시스템 조회·입력, 수수료 결제 등 실제 업무 실행 | 프로젝트 요건상 제외 |
| 모델 학습·파인튜닝 | 프로젝트 요건상 제외 |
| 실서비스 배포, 보안 인증 | 작은 평가셋과 제한된 문서 범위의 검증임 |

## 9. 목표 업무 흐름 (To-be)

```
담당자 질문 입력 (예: "D-4 어학연수생 시간제취업 허가 요건은?")
   │
   ▼
캐시 조회 (정규화한 원 질문 + 문서·색인·모델·프롬프트·검색 설정 버전)
   │
   ├─ 적중 → 저장된 답변 반환 (버전이 하나라도 바뀌었으면 적중으로 보지 않음)
   │
   ▼ 미적중
쿼리 리라이트 (구어체 → 매뉴얼 용어, 체류자격 약호는 그대로 유지)
   │   리라이트 실패 시 원 질문으로 진행
   ▼
BM25 검색 + Vector 검색 → 결합(RRF 등)
   │
   ▼
Reranker로 질문–청크 관련도 재평가 → 최종 근거 청크 선택
   │
   ▼
근거 충분 여부 판정 (판정 규칙은 dev.json으로만 조정)
   │
   ├─ 근거 충분 → 답변 + 출처 (문서명, 절, 쪽, 청크 ID)        status: answered
   │
   ├─ 근거 부족 → "제공된 문서에서 근거를 찾을 수 없음" 안내    status: no_evidence
   │
   └─ 호출 오류 → 오류로 표시 (근거 없음과 구분)
                  검색 오류 retrieval_error / 모델 오류 model_error / 시간 초과 timeout
   │
   ▼
담당자가 출처 원문을 직접 확인한 뒤 민원인 안내·심사 진행
```

> status 값은 `src/schemas.py`의 `AgentResponse.status`와 일치해야 한다. 오류 status(`retrieval_error`, `model_error`, `timeout`)는 평가에서 항상 실패로 집계하며, 올바른 "근거 없음"으로 세지 않는다.

### 9.1 최적화

두 최적화는 서로 다른 문제를 다루므로 둘 다 적용한다.

| 최적화 | 다루는 문제 | 규칙 |
| --- | --- | --- |
| 캐싱 | 같은 질문의 반복 처리에 드는 응답 시간·비용 (11.1절 우선순위 2·3) | 캐시 키는 정규화한 원 질문과 문서·색인·모델·프롬프트·검색 설정 버전으로 구성한다. 매뉴얼이 수시로 개정되므로(4절 6항) 버전이 바뀌면 이전 답변을 재사용하지 않으며, TTL을 함께 둔다. |
| 쿼리 리라이트 | 사용자 표현과 매뉴얼 용어의 불일치 (4절 3항) | 원 질문과 리라이트 결과를 모두 기록한다. `D-2-2` 같은 체류자격 약호와 숫자는 바꾸지 않는다. 리라이터에는 정답표(`expected_facts`, `evidence`)를 넣지 않는다. 오류 시 원 질문으로 검색한다. |

- 비교 실험(구성 A/B/C)에서는 두 최적화를 모두 끈다. 검색 방식의 차이만 비교하기 위해서다.
- 각 최적화는 구성 C에 하나씩 적용해 따로 평가한다.
  - 캐싱: 5문항 × (미적중, 적중, 버전 변경 후 재요청) = 15회. 버전 변경 후 이전 답변이 재사용되지 않음을 확인한다.
  - 쿼리 리라이트: 최종 평가 20문항 전체. 구성 C 대비 품질 변화, 추가 응답 시간, 리라이트 실패 수를 기록한다.

## 11. 우선순위와 성공 기준

**최종 평가 실행 전에 확정하고, 결과를 본 뒤 변경하지 않는다.** 목표 미달도 원인 분석과 함께 그대로 보고한다.

### 11.1 우선순위

**품질 > 응답 시간 > 비용**

- 오답이 부당한 처분과 민원인 피해로 이어질 수 있어 품질이 최우선이다.
- 담당자가 창구에서 사용하므로 응답 시간은 두 번째다. 다만 수 초의 추가 지연은 정확도가 높아진다면 허용한다.
- 호출 비용은 위 두 조건을 만족하는 구성 중에서 비교한다. 비용은 목표값을 두지 않으며, 구성별 모델 호출 수와 입출력 토큰 수를 실행 기록에 남겨 비교한다.

### 11.2 목표값 (최종 평가 20문항 기준)

| 지표 | 분모 | 목표 |
| --- | --- | --- |
| Hit@5 | 답변 가능 17문항 | ≥ 0.80 |
| 정답 충족 | 답변 가능 17문항 | ≥ 0.70 |
| 근거 적합 (인용이 실제 검색 결과이며 주장을 뒷받침) | 답변 가능 17문항 | ≥ 0.90 |
| 근거 없음 대응 | 근거 없음 3문항 | 3/3 |
| 응답 시간 중앙값 (성공 호출, 검색+생성 포함) | 성공 호출 수 | ≤ 10초 |

- 응답 시간은 중앙값으로 목표를 판정하되, 평균과 n(성공 호출 수), 시도 수, 오류·timeout 수를 함께 보고한다.

- 근거 적합과 근거 없음 대응 목표를 정답 충족보다 높게 잡은 이유: 이 업무에서는 답을 못 하는 것보다 틀린 근거로 단정하는 것이 더 위험하기 때문이다.
- 호출 오류·timeout은 실패로 집계하며, 올바른 "근거 없음"으로 세지 않는다.

### 11.3 채점 규칙

모든 실행은 0/1로 채점하고 판단 근거를 기록한다. 1명이 채점하고 다른 팀원이 교차 확인한다. LLM 판정을 쓰는 경우 사람 채점과 분리해 기록하며, 목표 달성 여부는 사람 채점으로만 판단한다.

| 지표 | 1점 | 0점 |
| --- | --- | --- |
| Hit@5 | 최종 검색 결과 상위 5개(구성 C는 rerank 후 순위) 안에 `evidence`의 `chunk_id`가 하나 이상 있음 | 그 외. 검색 오류는 0. 결과가 5개 미만이면 반환된 결과만으로 판정 |
| 정답 충족 | `expected_facts`를 모두 포함하고, 틀리거나 서로 모순되는 내용이 없음 | 핵심 사실이 하나라도 틀리거나 누락되거나 모순됨. 답변 가능 문항을 "근거 없음"으로 거절(과잉 거절). 오류 status |
| 근거 적합 | 인용한 청크가 모두 해당 실행의 검색 결과에 있고, 답변의 주요 주장마다 이를 뒷받침하는 인용이 있음 | 검색 결과 밖의 청크 인용. 주요 주장을 뒷받침하지 않는 인용. 인용 없음(과잉 거절 포함). 오류 status |
| 근거 없음 대응 | status가 `no_evidence`임. 또는 매뉴얼이 다루는 부분만 근거와 함께 답하고 나머지는 문서에 없다고 명시함 | 문서에 없는 내용을 단정함. 오류 status |

세부 규칙:

1. **Hit@5는 검색 지표다.** 답변 status와 무관하게 검색 결과로만 판정한다. 근거 부족 판정으로 답변을 거절했더라도 검색 결과에 정답 청크가 있으면 1이다.
2. **정답 충족과 근거 적합은 따로 채점한다.** 답이 맞아도 인용이 틀리면 정답 충족 1, 근거 적합 0이다.
3. **추가 내용**: `expected_facts` 밖의 내용은 감점하지 않는다. 다만 그 내용이 틀리면 정답 충족 0이고, 주요 주장인데 근거가 없으면 근거 적합 0이다.
4. **전제가 틀린 질문** (예: 허용되지 않는 활동의 절차를 묻는 질문): 매뉴얼 근거로 전제를 바로잡는 답이 정답이며, 해당 제한 사항을 `expected_facts`에 적는다. 없는 절차를 지어내 답하면 정답 충족 0이다.
5. **부분 근거 질문** (예: 수수료 금액은 있으나 납부 방법은 없음): 매뉴얼에 있는 부분을 인용과 함께 답하고 없는 부분은 "문서에 근거 없음"이라고 명시하면 근거 없음 대응 1이다. 없는 부분을 단정하면 0이다.
6. **오류 status** (`retrieval_error`, `model_error`, `timeout`): 모든 품질 지표에서 0이며, 근거 없음 문항에서도 올바른 거절로 세지 않는다. 재시도 결과는 원래 실행을 대체하지 않고 별도로 표시한다.

### 11.4 실패 분류

실패한 실행마다 **주 분류를 하나** 붙인다. 파이프라인 순서에서 처음 실패한 단계를 고른다.

| 주 분류 | 기준 | 확인 근거 |
| --- | --- | --- |
| 검색 누락 (retrieval miss) | 필수 근거 청크가 검색 후보 전체(rerank 전)에 없음 | 후보 목록 기록 |
| 순위 실패 (ranking failure) | 필수 근거 청크가 후보에는 있으나 답변 생성에 들어간 상위 청크 밖으로 밀림 | rerank 전·후 순위 |
| 생성 오류 (generation error) | 필수 근거가 컨텍스트에 있었는데 답변이 사실을 누락·오기·모순함 | 컨텍스트와 답변 대조 |
| 인용 오류 (wrong citation) | 검색 결과 밖의 청크를 인용하거나, 인용이 주장을 뒷받침하지 않음 | citation check 결과 |
| 근거 없음 대응 실패 (no-answer failure) | 근거 없음 문항에 단정함, 또는 답변 가능 문항을 거절함(과잉 거절) | status와 답변 |
| 시스템 오류 | `retrieval_error`, `model_error`, `timeout` | status |

분석용 태그 (여러 개 가능, 주 분류와 별도):

| 태그 | 기준 |
| --- | --- |
| 자격 혼동 | 질문과 다른 체류자격·세부약호의 근거로 답변 (예: D-2 질문에 D-4 근거) |
| 다중 근거 부분 회수 | `required: true` 근거가 2개 이상인 문항에서 일부만 검색됨 |
| 단서 조항 누락 | 핵심 요건은 맞으나 비고·"다만 ~한 경우" 등 예외 조건을 빠뜨림 |
