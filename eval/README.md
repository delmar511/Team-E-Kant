# 평가셋 (eval)

> 작성 상태: 초안 (팀 검토 필요)
> 관련 문서: `docs/problem.md` (성공 기준·실패 판정 기준)

---

## 1. 개요

| 파일 | 용도 | 문항 수 | 구성 |
| --- | --- | --- | --- |
| `dev.json` | 개발·튜닝용. 개발 중 자유롭게 반복 실행 | 10 | 답변 가능 8, 근거 없음 2 |
| `test.json` | 최종 평가용. 버전 고정 후 구성별(A/B/C) 1회 실행 | 20 | 직접 검색 10, 표현 변형·유사 조건 구분 7, 근거 없음 3 |

- 평가 대상 체류자격: **D-2(유학), D-4(일반연수)**
- 근거 문서: 하이코리아 「체류민원 자격별 안내 매뉴얼」 (판은 5절 버전 정보 참조)

## 2. 스키마

각 파일은 문항 객체의 JSON 배열이다. 필드명은 코드에서 읽기 쉽도록 영문으로 쓴다.

### 2.1 문항 필드

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `id` | string | 필수 | 문항 ID. 개발용 `DEV-001`~`DEV-010`, 최종 평가용 `TEST-001`~`TEST-020`. 한 번 부여하면 변경하지 않음 |
| `split` | string | 필수 | `dev` 또는 `test`. 파일과 일치해야 함 |
| `type` | string | 필수 | `direct`, `paraphrase`, `confusable`, `no_answer` 중 하나 (3절 정의 참조) |
| `visa` | string[] | 필수 | 관련 체류자격. 세부약호까지 쓸 수 있음. 예: `["D-2-2"]`, `["D-2", "D-4"]` |
| `question` | string | 필수 | 사용자(담당자)가 입력할 질문 원문 |
| `expected_facts` | string[] | 필수 | 정답에 반드시 포함되어야 할 핵심 사실 목록. 매뉴얼 원문에서 확인한 내용만 적음. `no_answer`는 빈 배열 `[]` |
| `evidence` | object[] | 필수 | 허용 근거 목록 (2.2 참조). `no_answer`는 빈 배열 `[]` |
| `no_answer_reason` | string \| null | 필수 | `no_answer`일 때 근거가 없다고 판정한 이유 (예: "매뉴얼에 해당 내용 없음", "허가 판정 요청으로 범위 밖"). 그 외 유형은 `null` |
| `verified_by` | string | 필수 | 매뉴얼 원문과 대조해 정답·근거를 확인한 팀원 |
| `verified_at` | string | 필수 | 확인 날짜 (`YYYY-MM-DD`) |
| `reviewed_by` | string | 필수 | 교차 검토한 팀원. `verified_by`와 달라야 함 |
| `reviewed_at` | string | 필수 | 교차 검토 날짜 (`YYYY-MM-DD`) |

### 2.2 근거(`evidence`) 필드

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `doc_id` | string | 필수 | 문서 목록의 문서 ID |
| `location` | string | 필수 | 원문 위치. 쪽·절·항목명 등 사람이 원문을 찾을 수 있는 형태. 예: `"p.45, D-2 체류기간 연장 제출서류"` |
| `excerpt` | string | 필수 | 근거가 되는 원문 발췌 (짧게) |
| `chunk_id` | string \| null | 필수 | 해당 청크 ID. 청킹 확정 전에는 `null`, 확정 후 채움 |
| `required` | boolean | 필수 | 정답에 꼭 필요한 근거면 `true`, 보조 근거면 `false` |

- **Hit@5 판정**: 상위 5개 검색 결과에 `evidence`의 `chunk_id` 중 **하나 이상**이 있으면 1, 아니면 0.
- **다중 근거 분석**: `required: true`인 근거가 2개 이상인 문항은, 그중 일부만 검색된 경우를 실패 분석에서 별도로 기록한다. (Hit@5는 전체 근거 회수율을 뜻하지 않음)

### 2.3 예시

**답변 가능 문항**

```json
{
  "id": "TEST-011",
  "split": "test",
  "type": "confusable",
  "visa": ["D-2-2", "D-4-1"],
  "question": "D-2 학사과정과 D-4 어학연수생의 시간제취업 허용 범위는 어떻게 다른가?",

    "(매뉴얼 원문에서 확인한 D-2-2 허용 범위)",
    "(매뉴얼 원문에서 확인한 D-4-1 허용 범위)"
  ],
  "evidence": [
    {
      "doc_id": "MAN-STAY-YYMMDD",
      "location": "p.00, D-2 시간제취업",
      "excerpt": "(원문 발췌)",
      "chunk_id": null,
      "required": true
    },
    {
      "doc_id": "MAN-STAY-YYMMDD",
      "location": "p.00, D-4 시간제취업",
      "excerpt": "(원문 발췌)",
      "chunk_id": null,
      "required": true
    }
  ],
  "no_answer_reason": null,
  "verified_by": "홍길동",
  "verified_at": "YYYY-MM-DD",
  "reviewed_by": "김철수",
  "reviewed_at": "YYYY-MM-DD"
}
```

**근거 없음 문항**

```json

  "split": "test",
  "type": "no_answer",
  "visa": ["D-2"],
```

## 3. 문항 유형 정의

| 유형 | 정의 | 예 |
| --- | --- | --- |
| `direct` | 매뉴얼 용어를 그대로 쓰는 질문. 해당 항목을 찾으면 바로 답할 수 있음 | "D-2 체류기간 연장 시 제출서류는?" |
| `paraphrase` | 같은 내용을 매뉴얼과 다른 표현(구어체, 동의어)으로 묻는 질문 | "어학당 학생이 알바하려면 뭐가 필요해?" |
| `confusable` | 비슷하지만 조건이 다른 자격·세부약호·업무를 구분해야 답할 수 있는 질문 | "D-2와 D-4의 연장 제출서류 차이는?" |
| `no_answer` | 매뉴얼에 근거가 없거나 시스템 범위 밖인 질문. 정답은 "정보 부족 안내" | "다음 달 개정 예정인 D-4 요건은?" |

- 최종 평가용의 "표현 변형·유사 조건 구분 7문항"은 `paraphrase`와 `confusable`을 합한 수이다.
- 유형이 애매하면 더 어려운 쪽(`confusable` > `paraphrase` > `direct`)으로 분류하고, 판단 근거를 변경 기록에 남긴다.
- `no_answer` 문항은 매뉴얼 전체를 검색해 실제로 근거가 없음을 확인한 뒤 확정한다.

## 4. 개발/평가 분리 원칙

1. **용도 분리**: 프롬프트, 근거 부족 판정 기준, 청크 크기, 검색 개수 등 모든 튜닝은 `dev.json`으로만 한다. `test.json`은 최종 평가에서 구성별 1회만 실행한다.
2. **결과 비공개**: 최종 평가 전에 `test.json` 문항으로 시스템을 실행하거나, 그 결과를 보고 설정을 바꾸지 않는다.
3. **중복 금지**: `test.json` 문항은 `dev.json` 문항의 단순 표현 변경이어서는 안 된다. 같은 매뉴얼 항목을 다루더라도 묻는 사실이 달라야 한다.
4. **ID 분리**: `DEV-`와 `TEST-` 접두어로 구분하며, 두 파일에 같은 ID나 같은 질문이 있으면 안 된다.
5. **정답 유출 금지**: 정답표(`expected_facts`, `evidence`)를 검색 색인 문서나 프롬프트, 쿼리 리라이터 입력에 넣지 않는다. 매뉴얼 원문이 색인에 포함되는 것은 정상이다.
6. **고정 후 변경 금지**: 고정 이후 목표 미달·오답을 이유로 문항을 교체하거나 삭제하지 않는다. 최종 결과를 보고 수정한 추가 실험은 본 평가와 분리해 기록한다.

## 5. 버전 정보

### 5.1 현재 버전

| 항목 | 값 |
| --- | --- |
| 평가셋 버전 | `eval-v0.1` (초안) |
| 근거 매뉴얼 | 「체류민원 자격별 안내 매뉴얼」 (판 정보는 `docs/corpus/` 각 파일 머리말의 `version`) |
| 청킹·색인 버전 | (청킹 확정 후 기입. `chunk_id` 매핑 기준) |
| Git 태그 | (고정 시 기입. 예: `eval-v1.0`) |
| `test.json` SHA-256 | (고정 시 기입) |
| `dev.json` SHA-256 | (고정 시 기입) |

### 5.2 고정 절차

1. 30문항 모두 `verified_by`, `reviewed_by` 확인 완료
2. 청킹 확정 후 모든 `evidence`의 `chunk_id` 채움
3. 해시 계산 후 5.1 표에 기입

   ```bash
   sha256sum eval/dev.json eval/test.json
   ```

4. 커밋 후 태그 생성

   ```bash
   git tag eval-v1.0
   git push origin eval-v1.0
   ```

5. 최종 평가 실행 기록에 평가셋 태그와 해시를 함께 남김
